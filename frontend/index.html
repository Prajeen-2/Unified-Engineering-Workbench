Parallel Architecture, Synchronization & Scalability Analysis C++17 Multicore Engineering

The Multicore Performance Lab utilizes a production-grade C++17 bounded thread pool (workbench::performance::ThreadPool). Worker threads are spawned during pool initialization and persist across task batches, eliminating the non-trivial overhead of operating-system thread creation (\(\approx 0.3 \text{ ms}\) per thread on Windows x64).

  • Thread Worker Loop: Each thread runs a continuous event loop waiting on std::condition_variable m_cvTask.
  • Lock Guard Discipline: Queue access is strictly protected via std::unique_lock<std::mutex> with zero lock leaking.
  • RAII Lifecycle: Pool destructor atomically signals m_stop = true, wakes all threads via notify_all(), and cleanly joins each thread.
  • Measurement Purity: Thread creation and warmup are performed before the benchmark timing region, ensuring that only pure floating-point numerical FEA computation is measured.

Work is distributed across workers using contiguous, cache-aligned chunk slices. For a workload of \(M\) simulation cases and \(p\) workers, the workload is partitioned into chunks of size \(C = \max(1, M / (8p))\).

  • Deterministic Slot Mapping: Results are written directly to pre-allocated disjoint indices outResults[start .. end - 1]. Result index \(i\) strictly corresponds to input case \(i\).
  • Zero Data Races: Because each worker writes exclusively to its assigned index range, no mutex locking is required during FEA computation.
  • False Sharing Immunity: Each ThermalSolveResult instance contains dynamic heap-allocated vectors, preventing false sharing on CPU L1/L2 cache lines (64 bytes).
  • Reproducible PRNG: The input workload is generated using a 64-bit Mersenne Twister (std::mt19937_64) with fixed seed 42, ensuring identical test cases across serial and parallel executions.

Parallel overhead arises from queue synchronization, thread wake-up latency, and barrier completion.

  • Task Chunking: By grouping cases into chunks rather than individual single-element tasks, queue lock acquisitions are reduced by a factor of 15× to 30×.
  • Barrier Synchronization: The main thread waits for batch completion via m_cvFinished.wait(...), which triggers only when the task queue is empty and active workers reach zero.
  • Sub-microsecond Precision: Repetition times are measured using std::chrono::high_resolution_clock (backed by the hardware QueryPerformanceCounter on Windows x64).
  • Median Filtering: Across the 5 measured repetitions, the median execution time is selected to eliminate operating system scheduling jitter and background interrupts.

Real-world parallel speedup is bounded by algorithmic and hardware architectural constraints.

  • Amdahl's Law: If serial fraction is \(s\), maximum speedup with \(p\) workers is \(S(p) = \frac{1}{s + \frac{1-s}{p}}\). In our batch solver, the parallelizable fraction \(1-s \approx 0.98\).
  • Heterogeneous Intel Architecture: The host CPU (Intel 13th Gen Core i5-13420H) features heterogeneous Performance Cores (P-cores) and Efficient Cores (E-cores) with different clock speeds and IPC. When scaling from 1 to 4 workers, task scheduling across different core types can affect parallel efficiency.
  • Memory Bus Bandwidth: As worker count increases, simultaneous memory accesses to L3 cache and RAM introduce bus arbitration latency.
  • Thermal Throttling: Sustained multicore workloads trigger power-limit throttling (PL1/PL2), moderating peak boost clock frequencies compared to single-core execution.
